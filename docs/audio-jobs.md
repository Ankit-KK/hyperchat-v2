# Background jobs and donation audio (Phase 8)

Replaces the legacy Edge Functions `generate-donation-tts`, `generate-donation-music`, `generate-donation-sfx`
and `transcribe-voice-sarvam` (and the fire-and-forget calls to them from the payment and moderation paths)
with a durable PostgreSQL job queue and a worker process. Pusher, the OBS audio queue and the bots are later
phases: they read the state Phase 8 writes (`donations.tts_audio_url`). Phase 9: the job's completion also
writes the realtime `audio-ready` event in the same transaction ([`realtime.md`](realtime.md)).

```
approval transaction (Phase 7 auto-approve / Phase 5 dashboard approve)
   └─ INSERT jobs(kind=donation_audio, dedupe_key=<donation id>)         same transaction
worker (python -m app.worker, hyperchat-worker.service, N slots)
   └─ claim: UPDATE … (SELECT … FOR UPDATE SKIP LOCKED LIMIT 1) + 3-minute lease
       └─ handler → R2 (this environment's bucket) → finish job + donation update   same transaction
```

## Jobs (`public.jobs`, migration 0011)
- **Columns:** `kind`, `dedupe_key`, `payload` (ids only: `{"donation_id": "<uuid>"}`), `status`, `attempts` / `max_attempts`, `available_at`, `locked_by` / `locked_until` (the lease), `started_at`, `completed_at`, `last_error` (a reason code, never a provider body), `result`, timestamps.
- **Statuses:** `queued` → `running` → `succeeded` | `failed`.
  - A partial unique index on (`kind`, `dedupe_key`) over queued/running jobs makes enqueueing idempotent; a new job is possible once the previous one finished.
  - A retry goes back to `queued` with a later `available_at`.
- **Claiming:** `FOR UPDATE SKIP LOCKED`, so concurrent workers never take the same job and never wait on each other.
  - A running job whose lease expired (crash, kill -9, lost connection) is claimed again by any worker. That counts as an attempt, and `last_error = lease_expired`.
- **Fencing:** every later write (finish, retry, release) requires `locked_by = <this worker>` and `status = running`. A worker that lost its lease can never complete, retry or release the job; its transaction (including the donation update) rolls back.
- **Graceful stop (SIGTERM):** the worker stops claiming and gives running jobs 50 s (systemd `TimeoutStopSec=60`). Jobs still running are then released without counting the interrupted attempt.
- **Retention:** the daily cleanup (`python -m app.cli cleanup`) deletes jobs finished more than 30 days ago and `tts_moderation_audit` rows older than 90 days (legacy retention).
- **Manual enqueue:** `python -m app.cli --env-file /etc/hyperchat/api.env enqueue-donation-audio <donation id>`. Historical donations are never enqueued automatically.

| kind | max attempts | backoff |
|---|---|---|
| `donation_audio` | 4 | 5 s × 2ⁿ⁻¹, ±20 % jitter, ≤ 60 s; `Retry-After` honoured (≤ 60 s) |
| `voice_transcription` | 3 | 30 s × 2ⁿ⁻¹, ±20 % jitter, ≤ 300 s |

**Retryable:** timeout, network, HTTP 429, 5xx, malformed provider response (incl. non-MP3 audio), R2 failure, database failure (the lease expires and the job is claimed again), unexpected errors.
**Permanent:** HTTP 401/403 (credentials), 402 (quota), other 4xx (rejected, `bad_prompt`), a moderation block, invalid voice id, audio over 5 MB or 60 s, an invalid or missing voice object.
A permanent failure or the last failed attempt fails the job and runs the kind's fallback in the same transaction: for donation audio, the silence URL.

## Donation audio (`donation_audio`)
The donation is re-read when the job runs. If it is gone, unpaid, no longer approved, or already has `tts_audio_url`, the job finishes as `skipped`. Otherwise, in the legacy order:

1. **hypersound**: nothing to generate.
2. **voice message**: nothing to generate. The URL must be this creator's Phase 6 upload key in this environment's bucket, and the object must exist.
3. **`!sfx <prompt>`**: ElevenLabs sound effect (10 s). At most 10 per donor per hour, and none while another of theirs is still queued.
4. **`!testmusic <prompt>`**: ElevenLabs music (10 s). At most 5 per donor per hour, one in flight.
5. **media**: TTS announcement "… And they sent a GIF / an image / a video." when the creator's TTS is on.
6. **text**: TTS when TTS is on and `amount_inr` ≥ max(₹40, the creator's TTS minimum).
7. **anything else** (TTS off, below the minimum, an empty or over-long command): the silent fallback.

- **Storage:** generated audio goes to `tts-audio/<creator uuid>/<donation uuid>.mp3`, a deterministic key built from database ids only.
- **No double charge:** before any paid call, the handler looks for that object. A previous attempt that generated and stored it but never reached the database is reused, never paid for twice.
- **Write rule:** `tts_audio_url` is only set while it is NULL, the donation is still paid and approved, and it has no voice message or hypersound. It is never overwritten.
- **Silence:** `system/silence.mp3` is ~1 s of silent MPEG frames generated by the code and uploaded once by the worker. Nothing references the legacy bucket.

**TTS text:**
- A random hype line for the amount tier (7 tiers × 20 lines, vendored from legacy) with the donor name and spoken amount, then the message.
- The message is HTML-entity-decoded (checkout stores it escaped), sanitised (tags, zero-width/bidi and control characters), with character runs and repeated phrases capped.
- Emoji become spoken names: Hindi CLDR names (vendored, pinned: `cldr-annotations-full@45.0.0`) for the default Hindi accent, otherwise English names from Python's Unicode data. Nothing is fetched at runtime.
- Donor text cannot inject ElevenLabs audio tags.

**Speech routing** (legacy, plus D4):
- `tts_voice_id` `moss_audio_*` uses MiniMax `t2a_v2` / `speech-2.8-hd`. Emoji-spam messages (more than 5 unique emoji) go to ElevenLabs when `el_voice_id` is set.
- Any other voice uses ElevenLabs when `el_voice_id` is set: `eleven_v3`, falling back to `eleven_multilingual_v2` without audio tags.
- Otherwise MiniMax with `HYPERCHAT_MINIMAX_DEFAULT_VOICE_ID`.
- Provider audio must be a valid MP3 (Phase 6 parser), non-empty, at most 5 MB and 60 s.

## Moderation (before every paid call)
- **Engine:** the legacy deterministic engine (`mod-1.1.0+dict-1.2.0`) is ported unchanged: dictionaries vendored, parity asserted decision-for-decision against a golden fixture produced by the legacy code.
- **Fail closed:** a missing `HYPERCHAT_TTS_MODERATION_HASH_KEY` or any error means no provider call and silent audio.
- **Audit:** a block writes a `tts_moderation_audit` row with HMAC-SHA256 of `<creator id>:<normalised donor name>`, never the name or the text.
- **Probe limit:** 3 blocks for a supporter within an hour block everything they send until the hour has passed.

## Voice transcription (`voice_transcription`, D1)
`GET|POST /api/v1/dashboard/streamers/{streamer}/donations/{donation_id}/transcription`
- **Access:** owner, linked account or admin. POST passes the Origin + CSRF check. Responses are `no-store`.
- **POST:**
  - **200** `{"status": "completed", "transcript": …}` when it exists.
  - **202** `{"status": "queued"|"running"}` after enqueueing (deduplicated).
  - **404** for an unknown donation or another creator's donation; **409** when there is no voice message.
  - **429** after 30 requests per creator per hour; **503** when transcription is unavailable.
- **GET:** `{"status": "none"|"queued"|"running"|"completed"|"failed", "transcript": …|null}`.
- **The job:**
  - Reads only that donation's own Phase 6 voice object: validated key, size-capped read (5 MB) from this environment's bucket. Never a URL from the request.
  - Sends it to Sarvam `speech-to-text-translate` (`saaras:v3`, mode `transcribe`).
  - Stores the transcript once in `donation_transcripts`. It is never re-run per dashboard view.

## Configuration (`/etc/hyperchat/api.env`, names only)
`HYPERCHAT_AUDIO_PROVIDERS_ENABLED` (default `false`), `HYPERCHAT_MINIMAX_API_KEY`, `HYPERCHAT_ELEVENLABS_API_KEY`,
`HYPERCHAT_SARVAM_API_KEY`, `HYPERCHAT_TTS_MODERATION_HASH_KEY`, `HYPERCHAT_WORKER_CONCURRENCY` (default 2),
`HYPERCHAT_MINIMAX_DEFAULT_VOICE_ID`.
- **Providers are called only** when providers are enabled **and** the provider's key is set. Otherwise donation audio resolves to silence and transcription answers 503.
- **Database role:** the worker uses the API's database role (`hyperchat_app`, D6).

## Logging
Job ids, kinds, attempts, durations and reason codes only. Never provider keys, request or response bodies, donor names or messages, transcripts or voice audio.
