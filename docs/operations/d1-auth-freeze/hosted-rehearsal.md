# D1 freeze and importer: hosted Supabase rehearsal (README step 12)

**Status: PLANNED, NOT RUN.** Nothing in this file has been executed against any hosted project. It refines step 12 of
[`README.md`](README.md) "Staging rehearsal" into the exact checks, commands, expected results, pass/fail and abort
criteria, cleanup and evidence needed before the production cutover. Record results in a copy of
[`hosted-rehearsal-results-template.md`](hosted-rehearsal-results-template.md).

## Why it is needed
The local rehearsal (2026-10-12; [`rehearsal-2026-10-12-local.md`](rehearsal-2026-10-12-local.md)) showed that Supabase's
role setup (supautils) does things plain PostgreSQL and the catalog functions do not predict. For example,
`has_parameter_privilege` said the dashboard role `postgres` could not set `session_replication_role`, yet it could.
Hosted projects may be configured differently again. Only executing the statements on a hosted project shows what the
role used at the cutover can and cannot do.

## Hard boundaries
- **Only** a newly created, empty, dedicated, disposable Supabase project made for this rehearsal, after the owner's
  approval (gate G1).
- **Never** the legacy production project, the unrelated `TAX CMS` project, the V2 DEV or production databases, real
  users, real emails, or real password hashes.
- **Data:** synthetic accounts only. Their bcrypt hashes are generated by the test project's own GoTrue from synthetic
  passwords; no hash is ever copied in.
- **No outbound auth email:** hosted Supabase sends real email. Mail to synthetic addresses bounces, and bounces can
  get the account's email sending restricted. So no flow that sends mail is used: no recovery, no user email-change
  request, no public sign-up with confirmation.
- **The importer's target** is a throwaway **local** PostgreSQL 17 container on the operator's workstation, never a
  V2 DEV or production database. `--apply` runs only into that container (gate G5).
- **No secrets in chat, files under git, or logs.** The database password, service-role key and anon key live only in
  a local file with mode 600, which is deleted at cleanup.
- **No Docker or Supabase stack on the VPS.** Round-trip timing from the VPS (README step 11) is a separate, separately
  approved step.

## What the owner provides (locally, never in chat)
- **Access:** to the Supabase organisation, to create (G1) and delete (G6) the project.
- **Credentials, written into the local `rehearsal.env` (mode 600):**
  - the new project's **database password**, set at creation;
  - its **project URL**, **anon key** and **service-role key**.
- **Files:** the project's **CA certificate** (Dashboard → Database settings → SSL configuration → download), saved
  locally with mode 600.
- **Connection strings:** the **session pooler** string (port 5432, user `postgres.<ref>`), and the direct host
  `db.<ref>.supabase.co`. The direct host is often IPv6-only.

## Workstation setup
On the operator's PC, inside the `d1-rehearsal` WSL distro.
- **Tools** (installed earlier): psql, Docker, Python with the backend dev requirements, `curl`, `jq`.
- **Working directory:** a new one, e.g. `/root/d1-hosted` (mode 700), outside the repository.
- **`rehearsal.env`** (mode 600):
  - `SUPABASE_URL`, `ANON_KEY`, `SERVICE_ROLE_KEY`;
  - `PGHOST`, `PGPORT`, `PGUSER` (session pooler), `PGDATABASE=postgres`, `PGSSLMODE=verify-full`,
    `PGSSLROOTCERT=/root/d1-hosted/supabase-ca.crt`.
- **Password:** in `/root/d1-hosted/.pgpass` (mode 600), with `PGPASSFILE` pointing at it. Never on a command line.
- **Each shell:** `cd /root/d1-hosted && set -a && . ./rehearsal.env && set +a && unset HISTFILE`.
- **The repository** at the commit under test: `git archive <main sha> database/etl docs/operations/d1-auth-freeze
  backend/app/__init__.py backend/app/auth/__init__.py backend/app/auth/bcrypt_format.py | tar -x -C /root/d1-hosted/code`.

**Never print a token.** API responses are written to files with mode 600 and only the needed fields are extracted
with `jq`. The SQL editor must **not** be used for the lock and concurrency checks: it cannot hold a transaction across
runs. Use psql sessions over the session pooler, **never the transaction pooler (6543)**.

## Checks
Each check has an ID, the command, the expected result and the pass/fail rule. "Record" means: copy the exact output
(sanitized) into the results file.

### H1: Identity, versions, connection path
```sql
-- psql (session pooler, verify-full)
SELECT version(), current_user, session_user, inet_server_addr() IS NOT NULL AS remote;
SHOW server_version; SHOW ssl;
SELECT name, setting FROM pg_settings WHERE name LIKE 'supautils.%' ORDER BY 1;
```
- **GoTrue version**, safely, with the anon key:
  `curl -s "$SUPABASE_URL/auth/v1/health" -H "apikey: $ANON_KEY" | jq '{version, name}'`.
- **Expected:**
  - PostgreSQL 15 or 17;
  - `current_user = postgres`;
  - `ssl = on`;
  - psql connected with `verify-full`;
  - a GoTrue version string.
- **Record:** the PostgreSQL and GoTrue versions, and the supautils settings (privileged role, allowed configs).
- **Also record** the role the dashboard SQL editor uses: run `SELECT current_user, session_user;` once **in the SQL
  editor**. A read-only query is fine there.
- **Pass:** connected with `verify-full`, and the versions recorded.
- **Fail or abort:** a TLS verification error on every reachable host. That blocks the importer path (H12).

### H2: The dashboard role's capabilities (catalog, read-only)
```sql
SELECT rolname, rolsuper, rolbypassrls, rolcreaterole FROM pg_roles WHERE rolname = current_user;
SELECT pg_get_userbyid(relowner) AS owner, relrowsecurity, relforcerowsecurity
FROM pg_class WHERE oid = 'auth.users'::regclass;
SELECT has_table_privilege('auth.users', 'SELECT')   AS sel,
       has_table_privilege('auth.users', 'UPDATE')   AS upd,
       has_table_privilege('auth.users', 'TRUNCATE') AS trunc,
       has_table_privilege('auth.users', 'TRIGGER')  AS trg;
SELECT has_table_privilege('auth.users', 'MAINTAIN') AS maint;          -- PostgreSQL 17+ only (errors on 15: record)
SELECT pg_has_role(current_user, 'pg_signal_backend', 'MEMBER') AS signal,
       pg_has_role(current_user, 'supabase_auth_admin', 'MEMBER') AS auth_admin_member;
SELECT has_parameter_privilege('session_replication_role', 'SET') AS repl_catalog;  -- informational: proved wrong locally
SELECT count(*) AS users FROM auth.users;                               -- 0 before H6 (an empty project)
```
- **Expected:** owner `supabase_auth_admin`, `relrowsecurity = true`, `postgres` with `rolbypassrls = true`, users 0.
- **Record:** every value.
- **Catalog answers alone never pass a check.** H3 tests each capability by executing it.

### H3: Capabilities by execution (every statement rolled back)
```sql
BEGIN; SET LOCAL session_replication_role = replica; SHOW session_replication_role; ROLLBACK;     -- (a)
BEGIN READ ONLY; SET LOCAL lock_timeout = '5s'; LOCK TABLE auth.users IN SHARE MODE; ROLLBACK;    -- (b)
BEGIN; SET LOCAL row_security = off; SELECT count(id) FROM auth.users; ROLLBACK;                    -- (c)
```
- **(a) replica mode:**
  - `replica` means the dashboard role **can** bypass a plain-enabled (`O`) trigger. That is a residual risk, not a
    failure.
  - `42501` means it cannot.
- **(b) the source lock:** success means `postgres` can take it.
- **(c) row security:** success means `postgres` is not subject to RLS.
- **Terminating a session (`pg_signal_backend`), proven by execution:**
  - Terminal 1: `SELECT pg_backend_pid(); SELECT pg_sleep(120);`.
  - Terminal 2: `SELECT pg_terminate_backend(<pid>);`.
  - Record `true` or `false`, and terminal 1's error.
- **Record:** each SQLSTATE and message.

### H4: Install and verify the freeze (gate G3)
```
psql -X -v ON_ERROR_STOP=1 -f code/docs/operations/d1-auth-freeze/freeze.sql      # run 1
psql -X -v ON_ERROR_STOP=1 -f code/docs/operations/d1-auth-freeze/freeze.sql      # run 2
psql -X -f code/docs/operations/d1-auth-freeze/verify.sql
```
- **Expected:**
  - both runs exit 0; run 2 prints only the "schema already exists" notice;
  - `verify.sql` returns exactly one row: `enabled O`, `tgtype 31`, empty column list, `has_when false`, function
    `hyperchat_ops.d1_auth_freeze_guard`, `plpgsql`, and `body_sha256 = 243e5a50f507b66ece282566ff76419e9c99963a841a09faa0b9003be0e0d760`.
- **Also check the custom setting:** the freeze script's `DO` blocks set a custom setting (`hyperchat_ops.freeze_was_always`).
  If supautils refuses it, run 1 fails. Record the error.
- **Pass:** both runs commit and `verify.sql` matches exactly.
- **Fail (blocks the cutover):** either run fails as the dashboard role, or the hash or shape differs.

### H5: ENABLE ALWAYS and safe re-runs
```sql
ALTER TABLE auth.users ENABLE ALWAYS TRIGGER hyperchat_d1_auth_freeze;   -- as postgres
```
- **Expected:** `42501 must be owner of table users`. The dashboard role is not the owner.
- **If it unexpectedly succeeds:**
  - `verify.sql` shows `A`;
  - run `freeze.sql` again as `postgres`; it must exit 0 and `verify.sql` must still show `A`;
  - then the replica-mode `UPDATE` in H7(c) must be **rejected**.
- **If it fails as expected:** there is no owner login on hosted projects, so "preserves `A` when run by the owner" and
  "a non-owner re-run fails safely while `A`" **cannot be exercised on hosted**. Record them as `NOT POSSIBLE ON
  HOSTED`. They are covered by the PostgreSQL 17 tests and the local Supabase image (`README.md`, Limitations).
- **Pass:** the behaviour is recorded. A failure here is expected and is **not** a blocker in itself.
- **Owner decision:** the replica-mode bypass stays an open residual risk (H7c).

### H6: Synthetic accounts (before the freeze is relied on)
**Order:** run H6 **before** H4, or after `unfreeze.sql`. With the freeze in place, account creation is rejected by
design.

Create three accounts with the admin API. The test project's own GoTrue hashes the synthetic passwords (bcrypt):
```
for n in canary victim observer; do
  pw="Rh-$(openssl rand -hex 12)"; printf '%s %s\n' "$n" "$pw" >> passwords.local   # mode 600, deleted at cleanup
  curl -s -o "create-$n.json" -w '%{http_code}\n' -X POST "$SUPABASE_URL/auth/v1/admin/users" \
    -H "apikey: $SERVICE_ROLE_KEY" -H "Authorization: Bearer $SERVICE_ROLE_KEY" -H 'Content-Type: application/json' \
    -d "{\"email\":\"d1-hosted-$n@example.com\",\"password\":\"$pw\",\"email_confirm\":true}"
done
jq -r '.id' create-*.json > ids.local
```
- **Expected:** 201 or 200 for each. `SELECT count(*) FROM auth.users` = 3. Hashes start `$2a$10$`; check that with
  `SELECT left(encrypted_password, 7)` only.
- **If `example.com` is rejected:** record it, and use another reserved domain such as `example.net`. Never use a real
  mailbox.
- **Sign in once as the canary** and keep the session in `session-canary.json` (mode 600):
  `POST /auth/v1/token?grant_type=password`.

### H7: Behaviour while frozen (freeze from H4 active)
**Frozen-field digest**, taken before and after every rejected action; it must not change:
```sql
SELECT count(*) || ':' || md5(string_agg(concat(id,'|',coalesce(email,'~'),'|',coalesce(encrypted_password,'~'),'|',
       coalesce(deleted_at::text,'~'),'|',coalesce(banned_until::text,'~')), E'\n' ORDER BY id)) FROM auth.users;
```

| ID | Action (anon key unless noted) | Expected |
|---|---|---|
| H7.1 | Password sign-in (canary), twice | 200 |
| H7.2 | Refresh-token grant, 3 times, chained | 200 |
| H7.3 | `GET /auth/v1/user` with the session | 200 |
| H7.4 | `PUT /auth/v1/user {"data":{"d1":"x"}}` (metadata) | 200; digest unchanged |
| H7.5 | `PUT /auth/v1/user {"password":…}` (user password change) | 500 `P0001 hyperchat_d1_freeze: password changes …`; digest unchanged |
| H7.6 | Admin `PUT /auth/v1/admin/users/<canary> {"password":…}` (service key) | 500 P0001; digest unchanged |
| H7.7 | Admin `PUT /auth/v1/admin/users/<observer> {"email":"d1-hosted-new@example.com"}` | 500 P0001 (email); digest unchanged |
| H7.8 | Admin `PUT /auth/v1/admin/users/<observer> {"ban_duration":"1h"}` | 500 P0001 (status); digest unchanged |
| H7.9 | Admin `POST /auth/v1/admin/users` (a new synthetic account) | 500 P0001 (creation); digest unchanged |
| H7.10 | Admin `DELETE /auth/v1/admin/users/<victim>` | 500 P0001 (deletion); the victim still exists |
| H7.11 | Public `POST /auth/v1/signup`, **only if G2 was approved** | 500 P0001; otherwise `NOT TESTED (sends email)` |
| H7.12 | SQL as `postgres`: `UPDATE` of `id`, `email`, `encrypted_password`, `deleted_at`, `banned_until`; `INSERT`; `DELETE` (each in `BEGIN … ROLLBACK`) | each `P0001 hyperchat_d1_freeze: …` |

**H7(c), the replica-mode bypass**, in a rolled-back transaction:
```sql
BEGIN; SET LOCAL session_replication_role = replica;
UPDATE auth.users SET email = 'x-' || email WHERE email = 'd1-hosted-observer@example.com';
ROLLBACK;
```
- **Expected locally:** `UPDATE 1`, the bypass. Record whether it succeeds on hosted. **Never commit it.**

**Not testable here, by design (no outbound mail):** user-initiated email change, recovery links and first-time OAuth.
Covered by the local rehearsal and by H7.9 (OAuth's first sign-in is an account creation, which H7.9 shows is
rejected).

**Pass:** H7.1–H7.4 return 200; H7.5–H7.12 are rejected with the freeze message; the digest is unchanged throughout.

**Fail (blocks the cutover):** sign-in or refresh fails while frozen, or any rejected action changes the digest.

### H8: The source lock and what it blocks (two psql sessions over the session pooler)
- **Session A** holds the lock as the intended `--apply` source role (`postgres` unless H10 shows a dedicated role can
  be used): `BEGIN READ ONLY; SET LOCAL idle_in_transaction_session_timeout = '60s'; LOCK TABLE auth.users IN SHARE
  MODE; SELECT 'held';` Keep it open; run session B's probes within 60 s.
- **Session B** probes, each `BEGIN; SET LOCAL lock_timeout = '2s'; <statement>; ROLLBACK;`:

| ID | Statement | Expected |
|---|---|---|
| H8.1 | `UPDATE auth.users SET last_sign_in_at = now() WHERE email = 'd1-hosted-observer@example.com'` | `55P03` lock timeout |
| H8.2 | The same, after `SET LOCAL session_replication_role = replica` (if H3a allowed it) | `55P03` |
| H8.3 | `TRUNCATE auth.users CASCADE` (inside the rolled-back transaction) | `55P03`, or `42501` before waiting. Record which. |
| H8.4 | `ALTER TABLE auth.users DISABLE TRIGGER hyperchat_d1_auth_freeze` | `55P03`, or `42501` (not the owner) |
| H8.5 | `DROP TRIGGER hyperchat_d1_auth_freeze ON auth.users` | `55P03`, or `42501` |
| H8.6 | `CREATE OR REPLACE TRIGGER …` (the definition from `freeze.sql`) | `55P03` |
| H8.7 | `SELECT count(*) FROM auth.users` | returns at once (reads are not blocked) |
| H8.8 | GoTrue sign-in (observer) started while A holds the lock for about 5 s, then `ROLLBACK` in A | 200 after A releases. Record the latency. |
| H8.9 | Any write whose answer is neither 55P03 nor 42501, i.e. it went through | **Abort and record**: the lock did not protect |

- **After A's `ROLLBACK` (H8.10):** `SELECT count(*) FROM pg_locks WHERE relation = 'auth.users'::regclass AND mode = 'ShareLock'` = 0.
- **Pass:** H8.1–H8.6 never succeed while the lock is held, H8.7 is immediate, H8.8 completes after the release.
- **Fail (blocks the cutover):** any write succeeds while the lock is held, or the intended role cannot take the lock
  at all (H3b).

### H10: Source role options and RLS fail-closed (gate G4)
As `postgres`:
```sql
CREATE ROLE d1_rehearsal_reader LOGIN PASSWORD '<synthetic, in .pgpass>';
CREATE ROLE d1_rehearsal_noperm LOGIN PASSWORD '<synthetic, in .pgpass>';
GRANT USAGE ON SCHEMA auth TO d1_rehearsal_reader, d1_rehearsal_noperm;                              -- record notices
GRANT SELECT (id, email, encrypted_password, email_confirmed_at, deleted_at, banned_until, confirmed_at)
  ON auth.users TO d1_rehearsal_reader, d1_rehearsal_noperm;
GRANT MAINTAIN ON auth.users TO d1_rehearsal_reader;                                                 -- PG 17+; record notices
SELECT r, has_schema_privilege(r, 'auth', 'USAGE'), has_column_privilege(r, 'auth.users', 'encrypted_password', 'SELECT')
FROM unnest(ARRAY['d1_rehearsal_reader', 'd1_rehearsal_noperm']) r;
```
- **Locally, every one of these grants only warned "no privileges were granted"** except the column `SELECT`. Record
  what hosted does.
- **If the reader got `USAGE` and column `SELECT`,** run the **report** with it (from `code/database`):
  `python -B -E -s -m etl.auth_readonly_report`. Answer the prompts with:
  - the pooler or direct host, the CA path, port 5432 and database `postgres`;
  - role `d1_rehearsal_reader.<ref>` if the pooler requires it;
  - target: the local container from H11.
- **Expected while the reader lacks `BYPASSRLS`:** `refused: source: row-level security on auth.users would hide rows
  from this role` (exit 2). This is the F14 fail-closed behaviour.
- **Then try** `ALTER ROLE d1_rehearsal_reader BYPASSRLS;` as `postgres`, and re-run the report. Expected: counts,
  `source_accounts` = 3.
- **If no dedicated role can get `USAGE` and `BYPASSRLS`:** the cutover source role is `postgres` itself, run with
  `--accept-writable-source-role`. Record that as the decision input.
- **Pass:** RLS that would hide rows is refused, and **some** role (dedicated or `postgres`) reads all 3 rows.
- **Fail (blocks the cutover):** no role can read `auth.users` without RLS filtering.

### H11: The importer end to end over TLS (gate G5)
**The local target:**
- **Start the database:** a throwaway `postgres:17` container on `127.0.0.1:5441`, trust auth on loopback, migrated

  - The name must not be `hyperchat`, `hyperchat_dev` or `hyperchat_restore_test`.
  - The head includes migration 0017, the import ledger.
- **Insert three V2 users,** as the container superuser, matching the hosted synthetic accounts: same email,

**The runs** (from `code/database`, source = the hosted test project; the prompts as in H10):

   - `eligible` 3;

**Then confirm on the target:**
- the three local rows hold `$2a$10$…` hashes, checked by prefix only;

**Pass:** TLS `verify-full` works through the real `main()`, and the dry run, `--apply` and the ledger behave as

## Abort criteria (stop, record, go straight to cleanup)
- **The wrong project:** any sign that the connection is not the new test project. That means a different project
  ref, `auth.users` holding rows that H6 did not create, or a name other than the approved one.
- **Unexpected cost:** any cost or plan prompt that is not $0.
- **An unprotected write:** any write that is not rolled back and should have been (H7c, H8.9).
- **A leaked secret:** a token, key or password appearing in output that would be kept.
- **Mail:** an email being sent (check Auth → Logs).
- **Unexpected changes:** anything changing outside the test project.

## Cleanup and proof (gate G6)
1. **Unfreeze** (H12), if not already done. Run `DROP ROLE d1_rehearsal_reader, d1_rehearsal_noperm;`, after
   revoking their grants if PostgreSQL asks.
2. **Delete the project:** Dashboard → Project Settings → General → Delete project.
   - **Proof:** the project list no longer shows it, and `$SUPABASE_URL/auth/v1/health` no longer answers.
   - Record the dashboard listing **without** keys.
3. **Local cleanup:** `docker rm -f` the target container, then
   `shred -u rehearsal.env .pgpass passwords.local ids.local *.json supabase-ca.crt`, then remove `/root/d1-hosted`.
   - **Proof:** `ls /root/d1-hosted` fails, and `docker ps -a` shows no rehearsal container.
4. **Billing:** confirm in the organisation's billing page that no additional active project or charge remains.
5. **Record:** each proof in the results file. The rehearsal counts as complete only when all four are recorded.

## Outcomes that block the production cutover
Any of these needs a fix or an explicit owner decision **before** the cutover:
- `freeze.sql` cannot be installed, or re-run, as the hosted dashboard role (H4);
- `verify.sql` does not match the pinned hash and shape (H4);
- `unfreeze.sql` cannot be run as the dashboard role (H12);
- sign-in or token refresh fails while frozen, or a blocked action changes a frozen field (H7);
- no usable role can take the `SHARE` lock (H3b, H8), or a write gets through while it is held (H8);
- no role can read `auth.users` without row-level security filtering (H10);
- TLS `verify-full` fails on every host the VPS can reach (H1, H11).

**Not blockers in themselves, but each needs the owner's recorded acceptance or mitigation:**
- the replica-mode bypass being available (H3a, H7c), with ENABLE ALWAYS impossible for the dashboard role (H5);
- `postgres` being able to terminate the importer's session (H3), which feeds the exit-4 window.
